Implement $1.

1. **Read the spec fully before any code.** Find it via `brief/build/INDEX.md` (builds in `_BUILDS/`, addendums in `_ADDENDUM/`). If the spec references counsel gates or a parent build, read those sections too.
2. **GROUND FIRST — and choose how.** The precondition is *"have I looked before I write"*, and it is unconditional: **no product code lands until you know what machinery already exists.** Extend what exists; duplicating an existing capability because nobody looked is the most expensive class of mistake here, and you cannot write against machinery nobody has told you exists. **What is a judgement is the ROUTE, not the requirement — and "no agent" is a legitimate answer.** On a wide, unfamiliar or cross-cutting surface, spawn the `grounder` with the spec's concept list; on a surface you can read in a handful of files, read them yourself and be done sooner than the spawn would have returned. Choose on the size and unfamiliarity of the surface, not on a default. If you do spawn it, do not idle while it runs: read the spec's referenced sections, open the migration file you will amend, draft the test fixtures. Treat collision and gap findings — its, or your own — as blockers to resolve, not notes.
3. **Non-negotiables apply to every line:** `org_id` + RLS on every table, `audit_log` on every state change, `consent_log` for POPIA events, amend-forward migrations only (append §N BUILD_XX sections to 001–012; NEVER new numbered files; NEVER touch 007/008), all Anthropic calls through `lib/ai/client.ts`, every env read through `lib/env.ts`, `NEXT_PUBLIC_APP_URL` for every absolute URL.
4. **Sequence phases as spec'd, commit per phase** (commit-as-we-go — never trust an uncommitted working tree). Production-dark behind the gates the spec names. Where a phase carries **mechanical bulk** — a codemod, a migrate-N-sites sweep, a rename — that is the shape worth handing to the `implementer` agent; whether this phase's bulk is worth a spawn is your call, and a ten-site sweep you can finish in three edits is not. **If you do spawn it: in this checkout, never `isolation: "worktree"`** (E10: a worktree is cut from `origin/main`, so on a feature branch the agent transforms a different tree from yours and its green gate proves nothing about yours). Give it the transform and its scope, and **in the same breath start the next concrete thing: draft the next phase's ESLint rule and its two probe fixtures while it runs.** If the sentence after the spawn ends in a full stop, the main session waits — measured, and it cost roughly 2× wall-clock in the cells where it happened. Keep the judgment sites and the SSOT/rule design in the main session.
5. **How many agents: none, one, or many — the work decides, and all three are correct answers.** There is no floor and no quota. A task you can finish in a few files wants **none**, and the doctrine in `CLAUDE.md` says so plainly: on a narrow read-and-classify surface, delegating loses. A single bounded mechanical transform wants **one**. Work that genuinely splits wants **many — and then issue them in ONE message**, because agents dispatched in separate messages are waited on one at a time while several tool calls in a single message overlap. Measured on the E17 arm-C cells: eight agents, eight separate messages, **peak concurrency of one** — 92.9 agent-minutes stretched across a 206-minute span. Part of that had to be serial and still does: a verify→fix→re-verify chain cannot be parallelised, because walk N reads the tree walk N−1 changed. The rest was avoidable. When the work splits — several reviewers each taking a different dimension of one diff, censuses over unrelated patterns, grounding two subsystems, an `implementer` sweep over files another agent will not touch — send them together. Judge by scope overlap, not by count: two agents on disjoint files are safe at any size, two on the same file are wrong at any size.
   **Whether to delegate is free; how is not.** When you do spawn, it is through this repo's own agents — `grounder`, `census`, `db-inspector`, `implementer`, `walker` — with the scope and artefacts each one expects, not a generic agent handed a paragraph. They carry tuned tool sets and the write-scope hook, so a mistake inside one is bounded; a general-purpose agent given the same task is not. Choosing none is always open; choosing *ad hoc* is not.
   **One hard boundary, mechanical rather than stylistic: only ONE process may run the test gate at a time**, agents and this session included. `npm run check` writes `node_modules/.vitest-count.json` and reads it back in the same command, and `node_modules` is a junction shared by every worktree and the main checkout — so two concurrent runs race on one physical file. A truncated read fails the gate for no reason; worse, a partially-collected run that reads the other's complete report goes green, which is the exact failure `check-test-floor.mjs` exists to catch. Fan out the reading and the analysis; keep the gate serial.
6. **Deviations are allowed but never silent.** Each deviation from spec gets flagged in the report with reasoning — the spec author decides whether it stands.
7. Finish with `/walk`, then `/wrap`.
